# 团队协作指南

> 四个人怎么用 Git 协作，看这一份就够了

---

## 一、第一次使用（每个人都要做一次）

### 1. 安装 Git

下载：https://git-scm.com/download/win

安装时一路默认，注意勾选：
- ✅ Git from the command line
- ✅ Use bundled OpenSSH
- ✅ Checkout Windows-style, commit Unix-style line endings

### 2. 配置身份（只需一次）

打开 **Git Bash** 或 **CMD**，执行：

```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱@example.com"
```

> ⚠️ **每个人必须用自己不同的名字**，否则提交记录分不清是谁改的。
>
> 建议格式：
> - A：`git config --global user.name "A-4G"`
> - B：`git config --global user.name "B-BootLoader"`
> - C：`git config --global user.name "C-MQTT"`
> - D：`git config --global user.name "D-SPI"`

### 3. 克隆仓库

```bash
cd E:\桌面\deepseek\玩\outputs
git clone https://github.com/Dversion-4396/STM32_OTA.git
cd STM32_OTA
```

> 如果提示要输入用户名密码：
> - 用户名：你的 GitHub 用户名
> - 密码：**不是账号密码**，是 **Personal Access Token**
>   获取方式：GitHub → Settings → Developer settings → Personal access tokens → Generate new token → 勾选 `repo` 权限

### 4. 安装 Keil

打开 `APP工程/project/STM32F103ZET6_Project.uvprojx`，能编译就算环境 OK。

## 二、日常开发流程（每天重复）

### 核心原则：**先拉后推**

```bash
# ===== 每天开始工作前 =====
git pull

# ===== 写代码 =====
# 打开 Keil，改你负责的文件

# ===== 提交前先看改了什么 =====
git status
git diff

# ===== 提交 =====
git add .
git commit -m "feat(A): 实现 CAT1_SendAT 函数"

# ===== 推送 =====
git push
```

### 完整示例（A 的一天）

```bash
# 早上 9:00 到实验室
cd E:\桌面\deepseek\玩\outputs\STM32_OTA
git pull
# 输出：Already up to date. 或 更新了 xxx 文件

# 打开 Keil，写 cat1.c 里的 CAT1_SendAT 函数
# ...写了 2 小时...

# 编译通过后
git status
# 输出：modified:   APP工程/user/api/cat1.c

git diff
# 看看具体改了哪些行，确认没误改

git add APP工程/user/api/cat1.c
git commit -m "feat(A): 实现 CAT1_SendAT，能收发 AT 指令"
git push

# 下午继续...
```

## 三、只改你负责的文件（重要）

**每个人只改自己的文件，不要动别人的。**

| 成员 | 可以改 | 不要改 |
|---|---|---|
| **A** | `APP工程/user/api/cat1.c` `cat1.h` | 别人的文件 |
| **B** | `BootLoader工程/user/api/boot.c` `boot.h` `stmflash.c` `stmflash.h` `main.c` | 别人的文件 |
| **C** | `APP工程/user/api/mqtt.c` `mqtt.h` | 别人的文件 |
| **D** | `APP工程/user/api/spi.c` `spi.h` `main.c`<br>`BootLoader工程/user/api/spi.c` `spi.h` | 别人的文件 |
| **全员** | 各自的分工文档 | **`common.h`**（改了要通知全组） |

### ⚠️ common.h 的特殊规则

`common.h` 里有 Flash 分区宏和 EEPROM 结构体，**两个工程必须完全一致**。

**如果要改**：
1. 先在群里说一声
2. 改完后**同步到另一个工程**
3. 两个人一起提交

## 四、提交信息怎么写

### 格式

```
类型(成员): 简短描述
```

### 类型

| 类型 | 用途 | 例子 |
|---|---|---|
| `feat` | 新增功能 | `feat(A): 实现 CAT1_SendAT` |
| `fix` | 修复 bug | `fix(B): 修复 Flash 半字拼装高低字节反了` |
| `docs` | 改文档 | `docs: 更新接线说明` |
| `refactor` | 重构 | `refactor(D): 拆分 spi.c 的读写函数` |
| `test` | 测试 | `test: 添加 W25Q128 自测用例` |
| `chore` | 杂项 | `chore: 更新 .gitignore` |

### 好的提交 vs 坏的提交

```bash
# ✅ 好
git commit -m "feat(A): 实现 CAT1_SendAT，能发 AT 收 OK"
git commit -m "fix(B): 修复 Flash_Write 长度非偶数时越界"
git commit -m "feat(D): W25Q128 读 ID 通过，返回 0xEF4018"

# ❌ 坏
git commit -m "改了一下"
git commit -m "update"
git commit -m "提交"
```

> **判断标准**：三个月后回来看，能不能知道这次改了什么。

## 五、遇到冲突怎么办

### 什么时候会冲突

两个人改了**同一个文件的同一行**，后推的人会冲突。

### 怎么解决

```bash
git pull
# 输出：
# CONFLICT (content): Merge conflict in APP工程/user/api/common.h
# Automatic merge failed; fix conflicts and then commit the result.
```

打开冲突文件，会看到：

```c
<<<<<<< HEAD
#define FLASH_BOOT_PAGE_NUM   16
=======
#define FLASH_BOOT_PAGE_NUM   14
>>>>>>> 1a2b3c4
```

**解决步骤**：

1. 和改这个文件的人**当面商量**，决定用哪个值
2. 手动改成最终版本（删掉 `<<<<<<<` `=======` `>>>>>>>` 这些标记）
3. 保存
4. 提交

```bash
git add APP工程/user/api/common.h
git commit -m "fix: 统一 FLASH_BOOT_PAGE_NUM 为 16"
git push
```

> ⚠️ **千万别乱选"用我的"或"用他的"**，尤其是 `common.h`。
> 选错了会导致两个工程结构体不一致，OTA 永远不触发。

## 六、常见操作速查

### 查看状态

```bash
git status              # 当前改了什么
git diff                # 具体改了哪些行
git log --oneline -10   # 最近 10 次提交
git log --author="A"    # 只看 A 的提交
```

### 撤销操作

```bash
# 撤销工作区的修改（还没 add）
git checkout -- 文件名

# 撤销 add（已经 add 了）
git reset HEAD 文件名

# 撤销最近一次 commit（保留修改）
git reset --soft HEAD~1
```

### 暂存当前工作（临时切分支）

```bash
git stash          # 保存当前修改
git stash pop      # 恢复
```

### 看看别人改了什么

```bash
git pull
git log --oneline -5
git show 提交ID
```

## 七、每天的协作节奏

### 建议时间表

| 时间 | 做什么 |
|---|---|
| 9:00 | `git pull` 拉最新代码 |
| 9:30 | 站会（15 分钟）：昨天做了什么、今天做什么、卡在哪 |
| 9:45-12:00 | 写代码 |
| 12:00 | **`git commit` + `git push`**（上午的成果） |
| 14:00 | `git pull` |
| 14:00-17:30 | 写代码 |
| 17:30 | **`git commit` + `git push`**（下午的成果） |

### 什么时候必须 push

- ✅ 每天至少 **2 次**（上午一次、下午一次）
- ✅ 一个功能写完了
- ✅ 要下班了
- ❌ 不要攒一整天再推

> **为什么要勤推**：
> 1. 万一电脑坏了，代码还在
> 2. 别人能看到你的进度
> 3. 冲突越早发现越好解决

## 八、不要提交的东西

`.gitignore` 已经帮你过滤了，但注意：

| 不要提交 | 原因 |
|---|---|
| `Objects/` `Listings/` | Keil 编译产物，几十 MB |
| `*.uvguix.*` | Keil 窗口布局，每台机器不同 |
| `*.uvoptx` | Keil 用户配置，每台机器不同 |
| `*.hex` `*.bin` | 编译产物 |
| `*.rar` `*.zip` | 压缩包 |

**检查方法**：

```bash
git status
# 如果看到上面这些文件，说明 .gitignore 没生效
```

## 九、出问题了怎么办

### Q: push 提示 "rejected - non-fast-forward"

```bash
git pull --rebase
git push
```

### Q: 不小心提交了大文件

```bash
# 从 git 里删除，但保留本地文件
git rm --cached 大文件
git commit -m "chore: 移除大文件"
```

### Q: 改错了想回到之前的版本

```bash
git log --oneline          # 找到要回到的提交 ID
git checkout 提交ID -- 文件名    # 只恢复某个文件
```

### Q: 完全搞乱了，想重新开始

```bash
# 放弃所有本地修改（⚠️ 会丢失未提交的代码）
git reset --hard HEAD
git pull
```

> **最后手段**：删掉本地目录，重新 `git clone`。
> 但**未 push 的代码会丢**，所以一定要勤推。
